Read-only. It now covers every migration including the two new ones, and it was
tested against a database rewound to production's exact shape — reporting
MISSING without crashing, and PARTIAL when an ALTER lands half-applied.

```bash
cd <app dir>
git pull                                            # needed: the checker itself is updated
mysql -u <user> -p attendance_db < database/migrations/check-status.sql
```

Expect these two to report **MISSING**:

```
2026-10-07_policies         MISSING  0/3 artifacts
2026-10-07_documents_s3     MISSING  0/4 artifacts
```

**Apply only what it reports MISSING.** If anything reports PARTIAL, stop and
inspect — that is the state where an ALTER died halfway.

If the three October 6th migrations (`shift_unpaid_break`, `month_closures`,
`regularisation_requests`) also report MISSING, apply those first, in date
order.

## 8. Two settings to fix while you are there

**`NEXT_PUBLIC_APP_URL` is stale.** It still says
`attendance.raceinnovations.in`; production is `worklens.raceinnovations.in`.
Fix it in `.env` on the server (the app reads `.env`, not `.env.local`) and
restart.

**S3 is not configured, deliberately.** `S3_BUCKET` is unset, so documents keep
using the database path exactly as before — nothing breaks. To switch to S3,
follow `docs/S3-DOCUMENT-STORAGE.md`. Note that **once `S3_BUCKET` is set there
is no fallback**: if the key is wrong, uploads fail rather than quietly
reverting. Verify the credentials first with:

```bash
npx tsx --env-file=.env scripts/verify-document-storage.ts
```

---

## 9. Rolling back

The code rolls back cleanly:

```bash
git reset --hard 8de69e6 && npm install && npm run build && pm2 restart all
```

The migrations do **not** need rolling back. They are additive — two new tables
and nullable columns — and the previous code never reads them. Leaving them in
place is safe and is the better choice: dropping them would lose any policy
somebody had already created.

---

## What this deploy does not change

- **Nobody is on a policy**, so every figure is computed exactly as before.
  Policies only take effect when deliberately assigned.
- **No existing column changes meaning**, and nothing is renamed or retyped.
  The mobile app shares this database and is unaffected.
- **`file_data` becomes NULLable** — a widening, so existing rows and any
  existing reader are unaffected.
- **Documents stay in the database** until a bucket is configured.
